# 0032. OIDC sign-in and credential encryption

Status: accepted; widened by ADR 0097 (editing identity providers); extended by ADR 0115 (numbered key versions and rotating the master key).

## Context

ID-2 requires OIDC as an alternative to local accounts, and AD-1 requires configuring it in the browser rather than in files. Better Auth's SSO plugin stores identity providers in the database, which fits AD-1. Reading its 1.7.6 source showed four things that needed decisions:

- It stores the OIDC client secret in plaintext, inside a JSON `oidcConfig` column.
- Its "no implicit sign-up" switch can be bypassed by the client (`requestSignUp`).
- Trusting the provider's `email_verified` claim is an instance-wide setting.
- By default any signed-in user may register up to 10 providers.

It also refuses identity providers on loopback or private addresses unless their origin is trusted, as protection against server-side request forgery.

## Decision

- **OIDC through `@better-auth/sso` 1.7.6** (MIT). Its SAML code and dependencies (samlify, xmldom, fast-xml-parser, all MIT) are installed but unreachable, because the api's route allowlist exposes only `POST /api/auth/sign-in/sso` and `GET /api/auth/sso/callback/<providerId>`. Registration, updates and every SAML route are 404 over HTTP.
- **Credentials are encrypted at rest with our own key.**
  - AES-256-GCM through a Drizzle custom column type (`packages/db/src/crypto.ts`), using a 32-byte master key from the environment (`LAKKA_CREDENTIAL_KEY`, or `credential_master_key` generated by `init`). The key is never stored in the database (PR-2, NF-S1).
  - The column's identity is bound in as associated data, so a ciphertext copied to another column fails to decrypt.
  - The stored format is `v1:<iv>:<ciphertext and tag>`. M2 adds key versions and rotation on top, for model provider credentials.
  - Applied to `sso_providers.oidc_config` (the client secret) and `auth_accounts.id_token`, which Better Auth leaves in the clear even with `encryptOAuthTokens`. Access and refresh tokens are encrypted by Better Auth itself (`encryptOAuthTokens: true`, with the auth secret).
  - The key is configured once per process at startup. Reading or writing an encrypted column before that throws; nothing is ever written in the clear by accident.
- **Only instance admins register providers**, and only with a session (`POST /api/sso/providers`). The plugin's `providersLimit` is 0 for everyone else. Admins list and delete providers; anyone may list their ids and display names, so the sign-in page can offer them. The client secret is write-only.
- **New accounts only where a provider's policy allows.** Our table `sso_provider_policies` holds `allow_sign_up` (default false) and optional `allowed_email_domains`, matched exactly and case-insensitively. A Better Auth `user.create.before` hook enforces it for every user created by an SSO callback. The plugin's own `disableImplicitSignUp` is left off because a client can bypass it. Existing users of a provider always sign in.
- **An email match never links accounts.** `trustEmailVerified` is off and domain verification is disabled, so a provider sign-in whose email belongs to an existing account is refused rather than linked. The plugin's required `domain` field is filled but grants nothing.
- **A provider that sends no email** is refused by the plugin (`missing_user_info`), since every user needs one (ADR 0027).
- **Identity providers on private networks** must be listed in `LAKKA_OIDC_PRIVATE_ORIGINS`. They are added to Better Auth's trusted origins, not to the api's origin check (ADR 0006).
- **Unexpected Better Auth errors** are rethrown to the api's error handler through `onAPIError.onError`, which logs them filtered and answers a generic 500. Otherwise Better Auth's router prints them with `console.error`, bypassing our logger.
- **Integration tests** sign in through a real OIDC provider, Dex v2.45.1 (distroless image, Apache-2.0), with a password login automated in place of a browser.

## Consequences

- Backups and database dumps hold no usable identity provider secret. Restoring needs the secrets volume too, which AD-2 already requires.
- A person provisioned through OIDC gets a principal on their first authenticated request, which the web app makes right after sign-in. Until then they do not appear in the admin user list.
- Per-provider trust for linking verified emails is not supported. Adding it later means keeping `trustEmailVerified` off and deciding linking in a hook.
- SAML, if ever built (v2), would need its routes added to the allowlist and a review of its XML parsing.
