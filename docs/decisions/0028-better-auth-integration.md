# 0028. Better Auth integration

Status: accepted

## Context

ID-2 requires local accounts (and OIDC, ADR 0032). The stack names Better Auth. Its defaults do not fit a self-hosted, fail-closed product: sign-up is public, rate limits live in memory, it can send telemetry, it logs email addresses, and its hooks run inside its own transaction. Version 1.7.5 was read at source level before writing this.

## Decision

- **Where it lives:** `packages/core/src/auth`. Better Auth is framework-free (a fetch handler), so core can own it (ADR 0020). The api only adapts HTTP to it.
- **Tables:** `auth_users`, `auth_sessions`, `auth_accounts` and `auth_verifications`, written by hand in `packages/db/src/schema/auth.ts` with snake_case columns. Three checks keep them consistent:
  - Better Auth's own check compares its configuration with the Drizzle schema on first use.
  - CI compares the Drizzle schema with the migrations.
  - Our migration runner compares the migrations with the database.
    Better Auth never inspects the database itself.
- **Identity link:** `principals.auth_subject` references `auth_users.id`. A principal is created only after its Better Auth user is committed: lazily in `authenticate`, or explicitly by `createLocalUser`. Better Auth's database hooks run inside its transaction, and inserting from another connection there could create a principal for a user that is then rolled back.
- **Reachable routes are an allowlist in the api:** `POST /api/auth/sign-in/email`, `POST /api/auth/sign-out` and `GET /api/auth/get-session`. Everything else under `/api/auth` is a 404, so new Better Auth routes stay closed until someone adds them on purpose.
  - Public sign-up is not exposed. Accounts are created server-side by `createLocalUser`, which first-run setup and invites will call.
  - Better Auth signs a new user in automatically. `createLocalUser` deletes that implicit session so no unused bearer credential is left behind.
- **Sessions** live in Postgres, with the cookie cache off and no secondary storage. Revoking a session or suspending a principal therefore applies to the very next request (ID-6).
- **Cookies:** prefix `lakka`, `HttpOnly`, `SameSite=Lax`, path `/`. They are `Secure` and `__Secure-` prefixed when the public URL is https.
- **Public URL and trusted origins** come from config:
  - `LAKKA_PUBLIC_URL`, else `https://LAKKA_DOMAIN`, else `http://localhost:LAKKA_HTTP_PORT`.
  - The default loopback install also trusts `127.0.0.1`.
  - A subpath is refused until NF-C4 is designed.
- **Cross-site protection:** Better Auth checks Origin only when a cookie is present. Our api hook refuses any state-changing request that has an untrusted `Origin`, cookie or not, which stops login CSRF. With no Origin, a request carrying a cookie must be `Sec-Fetch-Site: same-origin`.
- **Throttling:** Better Auth's rate limiter is on, with storage in Valkey through an atomic Lua script (rate limits belong in Valkey). If Valkey is down, auth requests fail (invariant 3). Client addresses come from `X-Forwarded-For`, which Caddy sets.
- **Telemetry:** `telemetry: { enabled: false }`, and `BETTER_AUTH_TELEMETRY*` environment variables are deleted before Better Auth initializes. Its environment flag would otherwise override the option. It reads them lazily, so deletion is effective.
- **Logging:** Better Auth's logger is routed into ours. Only the level survives as an event name (`better_auth.warn`); message text is dropped, because some messages contain email addresses. Errors keep their name, code and stack frames.
- **Secret:** `auth_secret` (32 random bytes), generated by `init` like the other secrets. `LAKKA_AUTH_SECRET` overrides it. `pnpm dev` generates one into `.dev-secrets/`, which is gitignored.
- **Passwords:** 12 to 128 characters. Better Auth hashes them with scrypt.
- **Email verification** is off: v1 does not assume an outgoing mail server (ID-7). Trust comes from how accounts are created (setup or invite).
- **Version:** 1.7.5. 1.7.6 was under 24 hours old at install; its changelog has no security fix that affects this configuration.

## Consequences

- Adding a Better Auth feature means adding its route to the allowlist, and usually a test.
- `auth_sessions.token` is stored in plaintext, which is Better Auth's design. Anyone who can read the database can take over sessions. The database is already the trust boundary for everything else, including provider credential ciphertext.
- OAuth tokens in `auth_accounts` should be encrypted once OIDC is in use (Better Auth's `encryptOAuthTokens`, ADR 0032).
- Sign-in throttling depends on Valkey being up. That is consistent with budgets, but operators should know.
