# 0026. Migration runner and when migrations run

Status: accepted

## Context

AD-4 and NF-O1 require forward-only migrations applied automatically at startup, and refusal to start on a schema mismatch. Drizzle 0.45's `migrate()` compares timestamps against the newest applied row only. It never detects a database that is ahead of the code (a downgrade), never checks hashes (an edited migration), silently skips an older migration that arrives after newer ones, and takes no lock. It also creates its bookkeeping table outside the migration transaction. api and worker start at the same time under compose.

## Decision

- Migrations are generated by drizzle-kit (`pnpm db:generate`) in its file format and recorded in its table (`drizzle.__drizzle_migrations`, sha256 of each file). They are applied by our own runner, `packages/db/src/migrate.ts`, never by `drizzle-kit migrate` or drizzle's `migrate()`.
- The runner holds a Postgres session advisory lock (a fixed key) for the whole check-and-apply. A process that cannot get the lock within 60 s fails with `MigrationLockTimeoutError`.
- Under the lock it refuses, with `SchemaMismatchError`, when:
  - the database has a migration this version does not include (ahead, or a downgrade)
  - an applied migration's hash changed (it was edited)
  - a pending migration is older than the newest applied one (diverged history)
  - the journal itself is out of time order
- Pending migrations are applied in one transaction, bookkeeping table included, so a failure leaves nothing behind. Migrations must therefore be transactional (no `CREATE INDEX CONCURRENTLY`).
- **Both api and worker** call `ensureDatabaseReady` (core) at startup: wait for Postgres, then migrate or refuse. Whichever gets the lock first applies; the other then finds nothing pending. A mismatch is fatal: the process logs `start_failed` and exits 1, and compose's restart policy keeps it from serving.
- `lakka migrate [--verify]` (image) and `pnpm db:migrate [--verify]` (development) run the same code by hand.
- Integration tests run against Postgres 16 (the supported minimum) and 18 (the default), each test in its own database inside one testcontainers Postgres per run.

## Consequences

- A downgrade, a hand-edited migration, or a mismerged branch stops the service with a clear message, instead of running against the wrong schema.
- Development must not edit applied migrations; generate a new one (CLAUDE.md already requires this).
- Every process that uses the database waits for the lock at startup. With small migrations this takes milliseconds; a long migration delays the second process until it finishes.
- When drizzle 1.0 is stable, its new migration folder layout (`drizzle-kit up`) needs matching support in `readMigrations`.
