# 0027. Identity schema

Status: accepted; widened by ADR 0097 (who may grant instance admin).

## Context

The tech spec sketches `principals`, `workspaces`, `memberships` and `api_keys`, and says `owner_principal_id` makes ID-5 and NF-S2 "true by design rather than something code review has to catch". It leaves open where the instance admin role lives (ID-3 has one, the sketch has no column for it), the id type, principal status values, and how email uniqueness works.

## Decision

- **Instance admin** is `principals.is_instance_admin`, true only for users. Workspace roles stay `admin` or `member` in `memberships`.
- **Ids** are UUIDv7, generated in the app (`packages/db/src/uuid.ts`). They are time-ordered, and Postgres 16 has no built-in `uuidv7()` (ADR 0010). Columns have no database default, so every insert goes through the app.
- **Principal status** is `active` or `suspended`. Deletion arrives with NF-P4.
- **Email** is unique case-insensitively through a unique index on `lower(email)`, with no `citext` extension. Users must have an email; keys must not.
- **Delegation rules are database constraints.** A check says a key has an owner and a user does not. Composite foreign keys onto `principals (id, kind)`, paired with generated columns holding the required kind, guarantee that:
  - a key's owner is a user, never another key
  - only users are workspace members
  - an `api_keys` row belongs to a key principal
    Keys cannot carry `auth_subject` or `is_instance_admin`.
- **Enumerations are `text` with check constraints**, not Postgres enum types. With forward-only migrations, changing a check constraint is simpler than altering an enum.
- **`api_keys.hash`** must be a 64-character lowercase hex SHA-256 digest. The plaintext secret has nowhere to go (PR-3 in spirit, and invariant 9).
- **No foreign key from `api_keys` to `memberships`.** Whether a key's owner still belongs to the key's workspace is checked at request time. A foreign key would either block removing a member or delete the key's audit trail.
- **Better Auth's tables** are generated by Better Auth's own CLI (ADR 0028), so they match what it validates at startup. `principals.auth_subject` (unique) holds the Better Auth user id.
- Generated migration files are excluded from oxfmt so they stay byte-for-byte as drizzle-kit writes them. CI fails if `pnpm db:generate` would produce a new migration.

## Consequences

- The strongest rule in the product (a key never has more permission than its owner) has a database-level backstop: even a buggy query cannot create a key owned by a key, or a key that is a workspace member.
- The generated `*_kind` columns are bookkeeping that queries should ignore; Postgres rejects writes to them.
- A user without an email address (some OIDC providers allow this) cannot be provisioned. ADR 0032 decides what to do when an identity provider omits the email claim.
