# M6 gate: tools and MCP

Status: passed, on amd64 and arm64 in GitHub Actions.

The manual run against a public OAuth MCP server, which ADR 0066 Q5 put in this gate, was done against Notion's hosted MCP server (below). Two people connected their own accounts; no tool was run in that session. Running a tool with a person's own token is shown by the automated Keycloak tests.

The checks below run in these CI jobs:

- `check`;
- `integration` on Postgres 16 and on Postgres 18;
- `image`;
- `out-of-process`, new in M6 (ADR 0073);
- `stack`: the acceptance suite from first-run setup, now with Keycloak, then both SDKs, Open WebUI and LibreChat, and the shutdown check.

The "Where it runs" column names the CI job that carries each check.

Gate (docs/roadmap.md): the exit criteria are acceptance criterion 18, per-user credentials shown working against a real MCP server, and the dispatch layer proven by running one tool out of process. What matters most: a tool can never do what the requesting user is not allowed to do.

- **TL-2 (OAuth):** `mcp-oauth.integration.test.ts` against our own authorization server, and the Keycloak tests above.
- **TL-3 and TL-4 (allowlist and asking first):** `mcp-tools.integration.test.ts`. Synced tools start off the allowlist and ask first unless read-only. Tool definitions come from the snapshot, not the live server.

- **TL-6 (audit):** `tool-dispatch.integration.test.ts`. Every call is recorded with principal, acting person, arguments, status and whose credential was used. Arguments are audited, never logged.
- **TL-7 (delimiting):** `tool-shape.test.ts` and `tool-loop.integration.test.ts`. Results are framed and cannot close their own frame, and the note that results are data comes first.
- **TL-8 (out of process):** above.
- **TL-9 (loop limit):** `tool-guard.test.ts` and `tool-loop.integration.test.ts`. The loop stops after 8 rounds, a repeated call ends it, and every round is reserved and settled on its own.

## Manual run: a public OAuth MCP server

ADR 0066 Q5 asks for one run against a public MCP server that implements the MCP authorization spec, recorded here. Any such server will do, for example Linear's, Notion's or Sentry's hosted MCP servers. One that offers dynamic client registration tests the most. Otherwise, register a client with the provider and enter it on the Tools page.

1. Start a stack from this commit: `docker compose up`. Open it at its public URL: `http://localhost:8080` by default, not `127.0.0.1`, or the OAuth callback will not find your session (ADR 0074).
2. As a workspace admin, add a model provider key and a model that can call tools, and make it the workspace default.
3. On the workspace's **Tools** page, add the server:
   - its HTTPS address;
   - "Each person's own account".

   A workspace admin may add a public HTTPS server.

4. On **Your connections**, connect your account. Sign in and approve at the provider, and check that you land back on Your connections with "Your account is connected to ...".
5. On **Tools**, press **Sync tools**. Enable one read-only tool, such as a search or list tool, and leave it not asking first.
6. In **Chat**, ask for something that needs the tool. Check two things:
   - the reply uses data only your account can see;
   - the tool's result shows under "What ... returned".
7. Have a second person repeat steps 4 and 6 with their own account at the provider, and check that they see their own data, not yours.
8. Optional: mark the tool as asking first, and check that chat asks before it runs.
9. Record the run below: server, the two accounts' outcomes, and anything that failed.

| -------------------------------------------------------- | ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Notion's hosted MCP server, `https://mcp.notion.com/mcp` | Connections worked | Per-person OAuth, with Lakka's client registered dynamically. Two people each connected their own account, and Test succeeded. No tool was enabled or run, so steps 5 to 8 were not done. |

Also done in M6:

- client-defined OpenAI `tools` are passed through, and their calls returned to the client, which lifts G6 (ADR 0066 H4);
- every round of a tool loop reserves and settles on its own, under one request id (invariant 4, ADR 0071);
- the acceptance stack has an MCP server with no dependencies, and a Keycloak.

## Known limits and open items

- **Deferred:**
  - the inbound MCP surface, with the outbound MCP server, in v2 (ADR 0066 Q1). The spec's surfaces table says so;
  - showing tool activity live while a reply streams, which would need a second non-standard field (ADR 0072);
  - tools over HTTP in an out-of-process runner, which would need a network with limited egress (ADR 0073).
- **Known limits:**
  - later rounds of a tool loop retry, but do not fail over to another model (ADR 0071);
  - tool results from earlier runs are kept in the history but not replayed on a new message (ADR 0071);
  - with Keycloak, tokens name the MCP server through an audience mapper, since Keycloak ignores RFC 8707 `resource` (ADR 0074);
  - the OAuth callback returns to the public URL, so an install reached at another address, such as `127.0.0.1` for `localhost`, loses the session on the way back (ADR 0074);
  - a server's tool definitions change only when an admin syncs (ADR 0069).
