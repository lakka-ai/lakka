# M1 gate: the spine and foundational spikes

Status: passed. The checks below run in CI on every change; this page records what
they show and where.

Gate (docs/roadmap.md): isolation verified; both spikes proven. Exit criteria: an admin can
finish first-run setup in a browser, invite a member, issue a key, and revoke both. Isolation
between workspaces is checked by calling the API directly, not by clicking through the UI. Both
spikes work on both architectures.

## Acceptance criteria reached in M1

- **AC 1, first-run screen with no edits:**
  - CI starts the stack from scratch on native Ubuntu runners for amd64 and arm64, and the first e2e test opens `/` and lands on setup.
  - The same suite passed on an Apple Silicon Mac with Docker Desktop.
- **AC 3, image size:** the image size budget of 1 GB (ADR 0023) is checked in the CI `image` job. Cold start is covered by the M7 gate.
- **AC 6, access revocation:** covered for keys and for sessions ending, as above. Ending open chat streams, through the event published on suspension (ADR 0031), is covered by the M5 gate.
- **AC 16, isolation:** covered for workspaces, members, keys and invites. The gates that add conversations, traces and usage extend the same tests.

## Known limits

- **Subpath deployment (NF-C4)** is not supported. Every URL the web app builds is relative, so it is a configuration change later (ADR 0033).
- **OIDC principals** are created on a person's first authenticated request after sign-in (ADR 0032). They do not appear in the People list before that request.
- **OIDC runs on amd64 only:** sign-in against a real provider (Dex) runs in the integration suite on amd64. The e2e suite does not include an identity provider.
