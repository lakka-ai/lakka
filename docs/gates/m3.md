# M3 gate: policy and routing

Status: passed. The checks below run in CI on every change; this page records what
they show and where.

Gate (docs/roadmap.md): ungated milestone, the classifier question was settled in discovery.
Exit criteria:

- acceptance criteria 11 to 13
- classification latency under 100 ms at p95 on reference hardware
- every request carries a recorded routing decision with its confidence and the rule that produced it

The evaluation set is self-written and provisional: the same person wrote the routes and the
tests, which tends to flatter accuracy. The margin above the bar is small, 0.825 against 0.8.
It should be replaced or extended with real, anonymised traffic once design partners provide
some (ADR 0045). "Every request" means every request that reaches a provider. A request
refused before dispatch has no usage row. If it was refused while resolving, for lack of a
model, its `policy.resolve_model` span still records that.

## Known limits

- **To revisit with real data:**
  - replace or extend the evaluation set with real traffic, and re-tune (ADR 0045);
  - the code route: only 18% of code messages reach it by classification. The code-fence and code-file signals cover the common cases;
  - overrides of a "not sure" decision are recorded but not summarized per route.
- **Performance note:** the benchmark also embeds a long message of 1,571 characters. Its p95 has reached 67.55 ms on a shared amd64 runner against the same 100 ms check, while the classification of a typical message stays near 3 ms. Watch it if runners get slower or longer messages become common.
- **Not measured:** the tech spec also asks for classification under 5% of time to first token. That needs live providers, which are not used (M2 plan, D10). At about 3 ms, it is 1% of a 300 ms first token.
